# DriveScope 改造アイデア(車載 Vlog 制作パイプライン向け)

- 作成: 2026-10-01。HEAD `e823e79`(#31 GPX SYNC 番号付け)時点のコードを読み、Vol007(2026-09-30 撮影)で JSON を実際に使った結果から書いた。
- 前提となる使い方:
  - 映像: DJI Osmo Action 6 + Osmo Nano の 2 台。
  - 音声: DJI Mic 3。Mic の時計を編集の基準にしている。
  - 編集: Python で session JSON を読む。HUD(速度・G・ミニマップ)、町名カード、カメラが止まった区間を埋める全画面テレメトリを描く。
- 優先度: **P1** = 次の撮影前に欲しい / **P2** = 編集の手間が大きく減る / **P3** = あると良い。

## 0. Vol007 で実際に困ったこと(このリストの根拠)

| 困ったこと | 実測 | 関係するコード |
|---|---|---|
| SYNC のタップ時刻が拍手とずれる | Mic の拍手からの差が −1.4〜+3.5 s。セッションごとにばらばらで、時刻合わせに使えなかった | `RecordingController.mark`(:190-202)が actor を 1 回 await した後の `engine.elapsed` を使っている。カメラに見える・聞こえる合図もない(`HUDButtons.swift:34-79`) |
| 途中で置き直した後の G が使えない | 朝の約 9 分、スマホが約 82° 回った状態で安定していた。JSON の補正は 1 つだけなので、編集側で回帰し直した | `MountSolver` は最も長い姿勢だけを解く。`calibrationUpdated` イベントに回転行列が入っていない(`TelemetryEngine.swift:221-230`) |
| 記録の開始が遅い | カメラより朝 74 s・夜 88 s 遅れた。冒頭の HUD は「—」表示 | 手動 START のみ |
| 自宅の住所・座標が生で出る | 朝の始点と夜の終点・ループが約 1 km しか離れておらず、編集側でぼかしを全区間に広げた | `places.fullAddress`、生の座標。プライバシー機能はない(`PlacePicker` / `SessionFinalizer`) |

**編集側で見つけた回避策(アプリに取り込める)**: 「路面の段差」による時刻合わせ。スマホの垂直加速度(3–20 Hz の包絡)と Mic の 15–60 Hz の包絡を、120 s 窓で相互相関した。iPhone − Mic = +2.21 / 2.30 / 2.68 s が、窓ごとに ±0.1 s で安定して出た。SYNC がなくても合う。

## 1. 時刻合わせ(SYNC)— P1

### 1-1. SYNC で「音」を鳴らす ★最重要
- 編集の基準は Mic の音声トラック。**Mic に録れる合図**があれば、サンプル単位で合わせられる。
- 実装案:
  - `AVAudioEngine` で既知のパターンを鳴らす。例: 2.5 kHz / 40 ms × 3 発、間隔 120 ms / 200 ms。車内の騒音に埋もれない高さと、誤検出しない並びにする。
  - 再生を予約した `AVAudioTime`(hostTime)を uptime に換算して、`sync.audioAt` として保存する。**タップ時刻ではなく、鳴った時刻**を記録する。
  - `AVAudioSession` は `.playback` + `.mixWithOthers`、音量は固定値にする(ユーザーの音量に左右されないように)。
- 編集側は、この 3 発のパターンを Mic とカメラ本体の音から検出するだけで合う。今は拍手を探して人が判断している。

### 1-2. SYNC で「光」も出す
- 全画面を白くフラッシュする(2〜3 フレーム)。
- カメラの画面に映る位置に置いたときに効く(§6)。
- 夜は明るすぎないよう、白ではなく最大輝度の 50% 程度にする。

### 1-3. タップ時刻を「押した瞬間」で取る
- `Button` の action の中で、`ProcessInfo.processInfo.systemUptime` を同期的に取って `mark()` に渡す。actor に入る前に取る。
- Watch の `pressedAt` と同じ扱いにする。

### 1-4. Watch と Live Activity から SYNC
- Watch は MARK のみで、SYNC は意図的に外してある(`WatchLink.swift:9-10`)。
- 手首で押すとスマホで音が鳴る、という形なら、運転姿勢のまま拍手と同時に押せる。

### 1-5. カメラ向けの「時計画面」モード
- 録画開始時に 3 秒だけ、各カメラにスマホを向けて映す使い方。
- 表示するもの: 大きな `HH:MM:SS.ff` と、**毎フレーム更新する QR(unix ms を入れる)**。
- 編集側は 1 フレームを読むだけで、カメラの時計とのずれが分かる(DJI のファイル名の時刻は 1 秒単位で、今回 +0.6〜+2.7 s ずれていた)。

### 1-6. 時計のアンカーを定期的に保存
- `(unix, uptime)` の組を 60 s ごとにイベントとして保存する。
- 今は `SessionClock` が START 時の 1 組だけ。長時間の記録で wall と uptime がずれても検証できる。

### 1-7. 路面の段差のシグネチャを出力(任意)
- 垂直加速度の包絡(3–20 Hz、50 Hz)を `vibration` として JSON に入れる。
- 編集側の相関がもっと楽になる。motion を出力しない `gpsOnly` / `eco` のプリセットでも合わせられる。

## 2. 車両座標の G・複数の取り付け姿勢 — P1

### 2-1. 取り付け姿勢の履歴を JSON に出す
- `MountSolver` のクラスタを使って `mounts: [{from, to, rotation[9], confidence, method}]` を出力する。
- 最も長い姿勢以外も、それぞれ HeadingFit で解く。区間が短い(< 60 s など)ものだけ `rotation: null` にする。
- `calibrationUpdated` と `mountChanged` のイベントにも回転行列を入れる。
- Vol007 の朝は 2 つ目の姿勢(約 9 分)を編集側で回帰し直した。これがアプリ側で出ていれば、その作業は要らなかった。

### 2-2. 車両座標の G を出力する
- motion に派生列 `longG, latG, vertG, mountId, handled` を出す(フィルタなしの生の値と、0.3 s の LPF 版)。
- `handled` = 持ち替え中。重力の角度が急に変わる、回転が速い、画面がオン、の組み合わせで判定する。
- 編集側がそれぞれに補正を実装し直さずに済む。

### 2-3. 符号の約束を schema に明記する
- `lat + = 左`(アプリ内部)と、HUD の表示、編集側の約束がずれやすい。
- `session.axes = {x: "forward", y: "left", z: "up"}` を JSON に入れておく。

## 3. 位置・速度の質 — P2

### 3-1. 10 Hz の融合トラックを出力する
- 1 Hz の fix の間を、速度・course・ヨーレート(ジャイロ)で推測航法して、次の fix に滑らかに合わせる(誤差は線形に配分)。
- `track10hz: {t, lat, lon, speed, heading}` として JSON に出す。
- `TelemetryInterpolator` の速度融合(:162-179)を位置にも広げる形になる。
- 使い道: ミニマップの点の滑らかな移動、1 秒より細かい境界、全画面マップのヘディングアップ回転。
- 効く理由:
  - 1 Hz では、50 km/h で 14 m ずつ跳ぶ。直線で補間すると、カーブで弧の内側を斜めに切る。
  - 誤差は 1 秒なら小さい。加速度に 0.01 G の偏りがあっても約 5 cm、ジャイロも 1° 未満。だから「1 秒ごとに GPS で正解に戻す」組み合わせで両方の長所が残る。
  - GPS の途切れ(Vol007 は最大 6 s)も同じ方法でつなげる。
- Vol007 の全画面マップ(半径 750 m、1 px ≈ 1.5 m)は、最も近い GPS 点を使っていたため、1 秒ごとに約 9 px 跳んだ。
- JSON に 50 Hz の motion と calibration が入っているので、**編集側(`drivescope_geo.py`)でも先に試作できる**。アプリ側で実装すると、走行中の HUD と Replay の地図も滑らかになる。

### 3-2. 速度の遅れ(約 0.6 s)を補正した列を出す
- PLAN §3:145 で既知の遅れ。
- 補正済みの `speedFused` を別の列で出す。生の値は残す。
- HUD の速度計と映像の加速がぴったり合う。

### 3-3. 低速時の方位
- 5 km/h 未満では course が無効になる。
- ジャイロのヨーを積分して `heading`(信頼度付き)を出す。
- 交差点で停止・発進するときの矢印やマップの回転が安定する。

### 3-4. 磁北基準の座標系
- `xMagneticNorth` は計画にあるが、未配線(`CoreMotionSources.swift:19`)。
- 停車中の方位の補助になる。

## 4. エクスポート・プライバシー — P2

### 4-1. プライバシーゾーン ★
- 設定で「自宅」などを登録する(中心 + 半径。既定は 500 m)。
- エクスポート時のオプション:
  - (a) ゾーン内の点を除く
  - (b) 座標を丸める
  - (c) places の `fullAddress` を市区町村レベルまでにする
- 始点・終点から N m を自動でトリムするオプションも付ける。
- JSON に `privacy: {zones: n, trimmedStartM, trimmedEndM}` を記録しておく。編集側はその範囲の地図を出さない。

### 4-2. マーカーの情報を増やす
- JSON の `markers` に `source`(phone / watch / liveActivity / key)と `pressedAt`(押した時刻)を入れる。今はイベントにしかない。
- `label` を付ける UI を作る。例: MARK を長押しすると「景色 / トーク / 見どころ / NG」を選べる。
- 編集側で、見どころ → 前方カメラの差し込み、NG → カット候補、に振り分けられる。

### 4-3. GPX の拡張
- 今の GPX には `ds:speed` / `ds:course` / `ds:hAcc` がある。
- 追加: `ds:latG` / `ds:longG` / `ds:peakLatG`(その 1 秒の平均と最大)、`ds:baroAlt`、`<wpt>` として sections(カーブのピーク G、停車)。
- 仕様上の扱い:
  - GPX 1.1 の `<extensions>` は、`xsd:any namespace="##other" processContents="lax"`。
  - 名前空間(`urn:drivescope:gpx:1`)を宣言し、`trkpt` の子の**最後**に置けば、スキーマ検証も通る。
  - 対応していないソフトは無視して、普通の軌跡として読む。
- 注意:
  - `trkpt` は緯度経度が必須の 1 点なので、50 Hz の G は入れない。1 秒ごとの要約までにする(細かい G は JSON / CSV)。
  - 気圧高度は `<ele>` に入れない。`<ele>` は他のソフトが GPS 高度として読む。Vol007 の気圧は開始時からの差で、GPS に合わせていた。
  - 符号と単位(latG の + = 右旋回、G = 9.80665 m/s²)は `<metadata><extensions>` かドキュメントに 1 回書く。
- GPX だけを読むツールでも、G の演出に使える。編集パイプラインは JSON を正とするので、GPX は他のソフトや他人に渡すとき向け。

### 4-4. CSV の基準点を選べるようにする
- 今は最初の SYNC が t = 0(`ExportMetadata.swift:411-414`)。
- SYNC ごとの CSV を出すか、基準にする SYNC を選べるようにする。カメラを止めて再開した区間ごとに合わせられる。

### 4-5. 1 日単位のエクスポート
- 同じ日のセッション(Vol007 は 3 本)をまとめて 1 つの ZIP / フォルダにする。
- ファイル名は `YYYYMMDD_HHMMSS_<title>.json`(今は日本語のタイトル)。
- 保存先を「ファイル › DriveScope/YYYYMMDD」に直接にできると、撮影フォルダにそのままコピーできる。

### 4-6. summary を増やす
- `peakG` の時刻と位置、最高速度の時刻、停車の回数と合計時間、走行時間(停車を除く)。
- 編集側の end card やルートカードがそのまま使える。

### 4-7. schema のバージョン管理
- 上の項目を足すときは `version: 2` とし、`docs/` に JSON schema を置く。
- 編集側の Python は version を見て分岐する。

## 5. 撮影当日の運用 — P2〜P3

### 5-1. 記録の自動開始 ★
- 開始のきっかけ: CarPlay / 車の Bluetooth の接続、または「走行を検出」(CMMotionActivity の automotive + 速度 > 10 km/h)。
- 「プリロール」: START の前の 2〜3 分を、メモリ上のリングバッファに位置と motion を保持しておき、START 時にさかのぼって保存する。
  - 今の「2 s より古い fix は捨てる」処理(`TelemetryEngine.swift:67`)とは、別の経路にする。
- Vol007 の「74 s / 88 s 遅れ」がなくなる。

### 5-2. 撮影前チェックリスト画面
- START の前に、以下をタップで確認する:
  - Mic の録音開始
  - 両カメラの REC
  - ND・向き
  - スマホを固定したか
- チェックした時刻をイベントとして残す。Vol007 では Mic の開始が 10 分遅れていた。

### 5-3. 夜の窓への映り込み対策
- 夜間(照度、または時刻)は HUD を暗い赤、または最低輝度にする。
- 明るい画面はフロントガラスに映り、前方カメラの映像に出る。

### 5-4. 熱対策
- `thermalStateChanged` は記録しているが、何もしていない(`DeviceEventMonitor.swift`)。
- `.serious` になったら、画面輝度を下げる・HUD の更新を 10 fps にする・motion を 25 Hz に下げる(イベントに記録する)。
- ダッシュボードに置くと、日中は熱で止まりやすい。

### 5-5. 持ち替えの検出を表示する
- 置き直しを検出したとき(`mountChanged`)に、画面上で「再キャリブ中」と表示し、短く振動させる。
- 運転者が「置き直したので、しばらく真っすぐ走ろう」と分かる。

## 6. スマホをカメラの画面内に置くべきか(運用の結論)

- **置けるなら、車内カメラの画面の端に入る位置がよい**。ただし必須ではない。
  - 利点:
    - SYNC のフラッシュや時計画面(§1-2 / §1-5)がそのまま映り、映像側の時刻合わせが確実になる。
    - 視聴者から見て、「この HUD はこのスマホの値だ」という説得力が出る。
  - 欠点:
    - 夜の画面の反射(§5-3)。
    - 通知が映る(集中モードを推奨)。
    - 日中の熱。
    - 画面を触る手が映る。
- **音による SYNC(§1-1)が入れば、置く位置は自由になる**。編集の基準の時計は Mic なので、音の合図が最も確実。
- **位置よりも大事なのは「動かないこと」**。取り付け姿勢が 1 つなら、補正も 1 つで済む。固いマウントに固定し、走行中は触らない。
